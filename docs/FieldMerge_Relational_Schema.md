## 1 Design status and conventions

This maps the agreed Chen business design to the implemented PostgreSQL schema using [FieldMerge Requirements](FieldMerge_Requirements.md) as its behavioral baseline. Structural migrations, reconciliation/review functions, deferred consistency triggers, and session-aware wrapper access are implemented and tested. Functional acceptance, representative browser workflows, operational recovery, query evidence, and targeted security boundaries are verified. See [database setup](../README.md) for commands and the complete catalog-backed dictionary for physical details.

PK = primary key; FK = foreign key; UQ = unique constraint. Columns are NOT NULL unless explicitly marked nullable. UUID values are generated by the server. Times use timestamptz and UTC at application boundaries. SQL identifiers use snake_case.

The nine relations are app_users, survey_campaigns, tree_records, accepted_versions, form_versions, submissions, field_changes, review_decisions, and audit_events. MongoDB collections are specified separately in [the document model](FieldMerge_MongoDB_Model.md).

## 2 Mapping decisions

| Chen construct | Relational mapping |
|---|---|
| Strong entity | Relation with its own PK. |
| TREE_RECORD identifies weak ACCEPTED_VERSION | accepted_versions has PK (record_id, version_no); record_id references its owner. |
| Campaign contains records | campaign_id FK in tree_records. |
| User authors submissions | author_id FK in submissions. |
| Record receives submissions | record_id FK in submissions. |
| Form describes submissions | form_version FK in submissions. |
| Version is base for submissions | Composite FK (record_id, base_version_no). |
| Submission contains changes | submission_id FK in field_changes. |
| Version compared against/applies change | Composite version references in field_changes. |
| User makes decision | reviewer_id FK in review_decisions. |
| Change resolved by decision | change_id FK plus UQ in review_decisions; zero or one committed decision per change. |
| Decision produces version | Nullable result version reference; unique when present. |
| User publishes version | published_by FK in accepted_versions. |
| Submission originates version | Nullable origin submission reference in accepted_versions. |
| Version follows predecessor | Composite self-FK and predecessor-number constraint. |
| Audit associations | Nullable user, record, and submission references in audit_events. |

The nine business entities need no extra many-to-many junction table. FIELD_CHANGE and REVIEW_DECISION retain their own identities/attributes. The later internal transport extension uses batch_items to associate upload positions with existing source submissions across batches; its separate schema is documented in the query/export/batch guide.

## 3 Relation definitions

### 3.1 app_users

| Column | Type | Constraint or meaning |
|---|---|---|
| user_id | uuid | PK |
| email | text | UQ; lowercase, trimmed, nonblank |
| password_hash | text | Nonblank password-library hash; never plaintext |
| display_name | varchar(120) | Trimmed and nonblank |
| role | text | surveyor or reviewer |
| is_active | boolean | Default true |
| created_at | timestamptz | Server creation time |

Accounts are deactivated, not deleted when referenced. A designated reviewer account performs baseline imports; automated publication records its responsible surveyor rather than inventing a third application role.

### 3.2 survey_campaigns

| Column | Type | Constraint or meaning |
|---|---|---|
| campaign_id | uuid | PK |
| name | varchar(160) | Nonblank |
| starts_at | timestamptz | Beginning of accepted observation reference window |
| ends_at | timestamptz | CHECK ends_at >= starts_at |
| source_dataset_id | text | Dataset identifier for attribution and import mapping |
| source_url | text | Attribution URL |
| import_mapping_version | text | Identifier of deterministic source mapping |
| created_at | timestamptz | Server registration time |

Seed exactly one campaign for the MVP. Its reference window must accommodate the demonstration's observations; the dataset's publication year is not implicitly the new campaign's observation window. The importer creates baseline versions separately from submitted observations.

### 3.3 tree_records

| Column | Type | Constraint or meaning |
|---|---|---|
| record_id | uuid | PK |
| campaign_id | uuid | FK survey_campaigns(campaign_id) |
| source_record_id | text | Nonblank external identity |
| imported_at | timestamptz | Baseline import time |
| is_active | boolean | Default true |
| created_at | timestamptz | Server identity creation time |

UQ (campaign_id, source_record_id). The campaign fixes the one dataset in use. This uniqueness constraint is deliberately scoped to the campaign, so a future separate campaign could reuse the original source identifier. Re-import skips existing identities and never overwrites later versions.

Each committed tree must have version 1. An implemented deferred database constraint trigger enforces that participation requirement at transaction commit; a foreign key alone cannot require a child row to exist.

### 3.4 accepted_versions

| Column | Type | Constraint or meaning |
|---|---|---|
| record_id | uuid | FK tree_records(record_id); part of PK |
| version_no | integer | Positive; part of PK |
| parent_version_no | integer nullable | Predecessor of this same tree |
| species | varchar(120) nullable | Normalized nonblank label, or unknown |
| health | text nullable | Good, Fair, Poor, or unknown |
| diameter_cm | numeric nullable | CHECK enforces 0 through 999999.99 and at most two meaningful decimal places; no implicit rounding |
| guard_damage | boolean nullable | True, false, or unknown |
| origin_submission_id | uuid nullable | Submission responsible for nonbaseline publication |
| published_by | uuid | FK app_users(user_id) |
| created_at | timestamptz | Server publication time |

PK (record_id, version_no).

- Composite self-FK (record_id, parent_version_no) → accepted_versions(record_id, version_no).
- Composite FK (origin_submission_id, record_id) → submissions(submission_id, record_id).
- CHECK: version 1 has null parent and null origin; later versions explicitly require parent_version_no IS NOT NULL, parent_version_no = version_no - 1, and a nonnull origin_submission_id. Explicit null checks matter because a SQL CHECK does not reject an unknown/null result by itself.
- For the nullable references above, use default MATCH SIMPLE semantics. A baseline version still has a nonnull record_id; MATCH FULL would incorrectly reject the partially-null optional reference.
- Parent arithmetic plus PK and self-FK makes a linear, gap-free chain per tree, provided deletion/update of history is prohibited. Publication still locks tree_records to assign the next version safely.
- Add the origin FK after submissions exists, resolving the schema creation cycle. Baseline rows can be inserted first because their origin is null.

Do not store duplicated current survey values on tree_records. The highest committed version number identifies current state. The physical migration deliberately uses unrestricted numeric plus bounds/precision CHECKs, since numeric(8,2) can silently round an invalid input before a constraint inspects it. It retains the same allowed value range while rejecting excess precision at the database boundary.

### 3.5 form_versions

| Column | Type | Constraint or meaning |
|---|---|---|
| form_version | text | PK; tree-v1 or tree-v2 initially |
| definition_id | uuid | UQ logical reference to MongoDB form_definitions |
| schema_hash | text | CHECK enforces a lowercase 64-character hexadecimal SHA-256 fingerprint |
| is_supported | boolean | Whether new intake may use it |
| published_at | timestamptz | Server publication time |

Form identifiers and definitions remain immutable after publication. Intake support may be disabled while the historical definition remains available. A SQL FK cannot verify a document in MongoDB; the server verifies definition identity/hash before enabling it.

### 3.6 submissions

| Column | Type | Constraint or meaning |
|---|---|---|
| submission_id | uuid | PK; also MongoDB source-document ID |
| author_id | uuid | FK app_users(user_id); authenticated surveyor |
| client_submission_id | uuid | Author-scoped retry identity |
| record_id | uuid | FK tree_records(record_id) |
| base_version_no | integer | Existing version of this record |
| form_version | text | FK form_versions(form_version) |
| payload_hash | text | Canonical client-content SHA-256; 64-character hexadecimal CHECK |
| batch_id | uuid nullable | Transport grouping, not request identity |
| observed_at | timestamptz | Claimed observation time |
| received_at | timestamptz | Server receipt time |
| state | text | State enumeration below |
| source_verified_at | timestamptz nullable | Server completed evidence identity/hash verification |
| requires_review | boolean | Clock/campaign warning prevents automatic changed-value publication |
| warnings | jsonb | Array of structured warning codes; default [] |
| rejection_reason | text nullable | Terminal validation explanation |
| lease_token | uuid nullable | Current processing claim token |
| lease_expires_at | timestamptz nullable | Bounded recovery lease expiry |
| last_error | varchar(2000) nullable | Bounded operational message without secrets |
| updated_at | timestamptz | Last workflow update |
| verified_patch | jsonb nullable | Sealed verified scalar SQL projection after source checks; migration 002 |
| reconciliation_result | jsonb nullable | Immutable original reconciliation receipt; migration 002 |

UQ (author_id, client_submission_id). UQ (submission_id, record_id) supports same-record composite references from downstream relations. Composite FK (record_id, base_version_no) → accepted_versions(record_id, version_no).

State values: awaiting_document, ready, processing, needs_review, partially_applied, applied, no_change, resolved, rejected. A ready/processing/successful or review state requires source_verified_at. A rejected item may or may not have verified evidence depending on when validation failed. Invalid requests lacking a valid identity/base are rejected before a submission row can be inserted.

lease_token and lease_expires_at are either both null or both nonnull. Only a valid processing claim may publish. On a committed outcome, clear the claim. A retry worker can reclaim expired processing work through a protected function.

### 3.7 field_changes

| Column | Type | Constraint or meaning |
|---|---|---|
| change_id | uuid | PK |
| submission_id | uuid | Parent submission |
| record_id | uuid | Guard column for same-record composite references |
| field_name | text | species, health, diameter_cm, or guard_damage |
| base_value | jsonb | Typed normalized scalar; JSON null means unknown |
| proposed_value | jsonb | Typed normalized proposed scalar |
| compared_value | jsonb | Value at compared_version_no |
| compared_version_no | integer | Version used in latest classification |
| classification | text | no_change, compatible, already_represented, or conflict |
| state | text | pending, applied, rejected, no_change, or already_represented |
| pending_reason | text nullable | value_conflict, intervening_edit, clock_warning, or campaign_warning |
| revision_no | integer | Positive; increment whenever mutable review context changes |
| applied_version_no | integer nullable | Version that actually applied this field change |
| updated_at | timestamptz | Server update time |

UQ (submission_id, field_name). UQ (change_id, record_id). Composite FK (submission_id, record_id) → submissions(submission_id, record_id). Composite version FKs for (record_id, compared_version_no) and (record_id, applied_version_no) → accepted_versions.

Use MATCH SIMPLE for optional applied-version references. CHECK: applied state iff applied_version_no is nonnull; pending state requires a pending_reason, other states require it null. UQ (record_id, applied_version_no, field_name) prevents two change rows claiming the same changed field in one version; default null-distinct uniqueness allows multiple unapplied proposals.

SQL NULL is prohibited in the three scalar JSONB columns. Use JSON null for an explicit unknown value. Reject objects and arrays, and validate each scalar's type/domain according to field_name using a database validation helper. Omitted fields have no row. Do not infer boolean false from numeric zero.

A history inconsistency aborts publication and becomes an operational integrity error; it is not a successfully stored change classification. Clock warnings may leave classification compatible while state is pending with pending_reason=clock_warning.

### 3.8 review_decisions

| Column | Type | Constraint or meaning |
|---|---|---|
| decision_id | uuid | PK |
| change_id | uuid | UQ; one committed terminal decision per proposed field |
| record_id | uuid | Guard column matching the target field change |
| reviewer_id | uuid | FK app_users(user_id); must have reviewer role |
| client_decision_id | uuid | Reviewer-scoped retry identity |
| request_hash | text | Fingerprint of the validated decision request; 64-character hexadecimal CHECK |
| expected_version_no | integer | Accepted version seen by reviewer |
| expected_change_revision | integer | Pending revision seen by reviewer |
| action | text | accept_proposal, keep_current, or replace |
| chosen_value | jsonb | Valid typed scalar, including JSON null |
| reason | varchar(2000) | Trimmed nonblank explanation |
| result_version_no | integer nullable | Newly produced version; null if accepted state did not change |
| created_at | timestamptz | Server decision time |
| decision_result | jsonb nullable | Immutable original decision receipt; migration 003; protected wrappers populate it |

UQ (reviewer_id, client_decision_id). Composite FK (change_id, record_id) → field_changes(change_id, record_id). Composite version FKs for expected and result versions reference accepted_versions. UQ (record_id, result_version_no) allows at most one decision to produce a particular version, while allowing multiple null results.

keep_current requires null result_version_no. For a changed value, result_version_no must equal expected_version_no + 1. Equality alone does not establish a correct decision: a protected transaction checks latest version, pending revision, actor role, chosen value, and origin consistency before committing. Failed/stale handled HTTP attempts are independent security_events, not terminal decisions or business audit rows that would disappear on rollback.

### 3.9 audit_events

| Column | Type | Constraint or meaning |
|---|---|---|
| event_id | bigint identity | PK |
| actor_id | uuid nullable | FK app_users(user_id); null for system recovery |
| record_id | uuid nullable | FK tree_records(record_id) |
| submission_id | uuid nullable | FK submissions(submission_id) |
| event_type | text | Defined event code |
| event_data | jsonb | Structured object with safe context and version references |
| created_at | timestamptz | Server event time |

If both submission_id and record_id are present they must refer to the same tree; an implemented trigger enforces this. The schema permits either reference to be absent for relevant system events. Failed handled HTTP requests are recorded separately in security_events. No passwords, session tokens, or credentials belong in event_data. Identity sequence ordering is not proof of transaction commit order; use the actual version chain to reconstruct accepted state.

## 4 Referential actions and normalization

Use restrictive deletion for referenced users, campaign, records, versions, submissions, changes, forms, and decisions. Deactivate users/records and disable forms instead of cascading away evidence. No application UPDATE/DELETE is granted on accepted_versions, review_decisions, or audit_events. Publication updates workflow tables only through protected functions; MongoDB drafts have their own permitted lifecycle.

Identity, accepted values, source forms, proposals, and decisions are separated by purpose. Full snapshots deliberately repeat unchanged values for simple reads; immutable version history makes that repetition controlled. Source documents retain optional evidence rather than spreading repeated observations across canonical scalar columns.

record_id in field_changes and review_decisions is deliberate physical redundancy: it can be obtained through their parents but enables same-record composite FKs. These two physical relations should not be advertised as strictly 3NF because of that transitive dependency. A strict-3NF alternative removes those guard columns and uses triggers to check all same-record references. The selected design favors declarative referential protection and prevents guard values from diverging through composite FKs. The report should disclose this tradeoff rather than claim universal normalization.

## 5 Provenance and intervening edits

Do not create a separate duplicated current-state relation or assign every value to a snapshot's publisher. For any (record_id, version_no, field_name):

1. Find the most recent actual accepted value change to that field at or before the requested version by comparing neighboring snapshots with null-aware equality.
2. If none exists after version 1, the source is the baseline import identified by the tree/campaign and version 1.
3. Otherwise find the applied field_changes row linked to that changed version and field. It supplies the source submission.
4. If a terminal review_decision exists for that change, include reviewer/action/reason. For a reviewer replacement, chosen_value is authoritative; proposed_value may be different.

H in merge rule M05 is true if any neighboring snapshots after the base actually differ for the field, even when the latest value returned to the base. Keep-current decisions and already-represented proposals do not alter provenance or count as intervening value changes.

The implemented deferred consistency trigger verifies that every nonbaseline changed field has exactly one applying field_change, and that every applying change corresponds to a real value difference in its claimed version. This is the key bridge between historical snapshots and their explanations.

## 6 Constraints that require protected logic

| Rule | Enforcement beyond ordinary PK/FK/CHECK |
|---|---|
| Every committed tree starts with version 1 | Deferred constraint trigger after baseline import. |
| Safe latest-version assignment | Lock tree_records row; read latest version in the same publication transaction. |
| Surveyor/reviewer role and active account | Protected functions with server-authenticated actor context; no direct table mutation grant. |
| Base/current/proposed values and classifications | Database merge function reads actual snapshots, validates scalar domains, and checks history. |
| Sealed source evidence verified before publication | Intake verification boundary plus SQL source_verified_at gating; SQL cannot inspect MongoDB directly. |
| Decision expected version and change revision still current | Lock target record and pending change; compare inside transaction. |
| Applied changes match snapshot differences | Deferred cross-relation consistency trigger. |
| Version origin matches change's submission | Publication validation and deferred consistency trigger. |
| Chosen value and result match action | Decision function validates and commits all related rows together. |
| Terminal workflow and audit immutability | Restricted grants plus mutation-blocking triggers for immutable relations. |
| Optional audit references agree | Trigger when both record and submission are present. |

CHECK constraints must not be used to make unsupported cross-table guarantees. PostgreSQL documents their intended row-level use and recommends appropriate relational constraints or triggers for other rules [1].

## 7 Initial indexes and views

PK/UQ constraints supply their own supporting indexes. Plan additional indexes only where they support actual access patterns:

- tree_records(campaign_id) when not already covered by the campaign/source unique index.
- submissions(record_id, received_at), (author_id, received_at), and (state, lease_expires_at).
- field_changes(submission_id), plus a partial pending queue index on (record_id, updated_at) WHERE state='pending'.
- field_changes(record_id, applied_version_no) for provenance lookup where the existing uniqueness index is not sufficient.
- review_decisions(reviewer_id, created_at).
- audit_events(record_id, created_at) and (submission_id, created_at).

The saved query/performance suite measures selected existing index alternatives on representative synthetic history; see [query evidence](FieldMerge_Query_Demonstrations.md). The catalog-backed dictionary lists the actual 43 indexes, including PK/UQ indexes. The list above describes access intentions rather than asserting that every candidate became a separate index.

Views: latest_accepted_records; pending_field_reviews with actual current snapshot; submission_outcomes; field_value_provenance. A pending comparison stored on a change may be stale, so the reviewer view must also show the latest accepted version and require a fresh approval token.

## 8 Implementation order and checks

Create users/campaign/forms, records, versions without its origin FK, submissions, the deferred origin FK, field_changes, review_decisions, then audit_events. Add indexes and read views, then validation helpers, protected functions, consistency triggers, and role grants. Initial DDL alone does not implement the full workflow or access-control guarantees.

Disposable database tests verify weak composite keys, same-tree FK rejection, version-1 participation, linear parent chains, null/false/zero distinctions, retry uniqueness, one terminal decision per change, JSON scalar validation, provenance links and denied direct mutation. All 35 functional acceptance scenarios also pass through the implemented API/workflows, including concurrency and failure recovery; see [acceptance evidence](FieldMerge_Acceptance.md).
